# Cops and Robbers: agent rules

- `TODO.md` is the shared ledger for every agent and worktree. Edit it only on main, in the main checkout; from a worktree, read it with `git show main:TODO.md`.
- Exception: an issue found on a branch about that branch's own unmerged code goes under Issues in the branch's `TODO.md` and reaches main with the merge. Anything else you find goes into main's `TODO.md`.
- When work starts, move its line from Ideas to In progress on main (with the branch, or "design"), move every issue it folds in under it as a sub-item, keep it current as the work moves, and delete it with its sub-items once the work is merged and checked.

In existing worktrees, read the current project guidance with `git show main:AGENTS.md`. Record deferred review findings and issues noticed in passing under Issues, with the affected file and the observable problem. Order them by player impact, then host or panel problems, cosmetics, and maintainer-only work. Delete resolved entries once checked.

## Design and implementation

- Use the repo-local [Superpowers v7.0.2 skills](https://github.com/obra/superpowers/tree/22f0b463e7a5e579904dd6211a520321035526f7/skills) for feature design, planning and implementation. Codex uses `.agents/skills/` and Claude Code uses the same files through `.claude/skills/`. If a skill is missing from the session list, read its local `SKILL.md`. See the [Codex tool mapping](.agents/skills/using-superpowers/references/codex-tools.md).
- For new features, agree on the design with the user, write the spec in `docs/superpowers/specs/` and the task plan in `docs/superpowers/plans/`. Have the spec and plan reviewed and fix findings. Open review-ready documents in Ghostwriter when handing them to the user with `setsid -f ghostwriter "<file>"`. Begin implementation once the user approves the plan and authorizes the build. Use subagent-driven development by default unless the user explicitly chooses another approach.
- Write feature specs for the person deciding how the game should play. Give full gameplay specs explicit Why, Goals, Non-goals (adjacent work outside the feature) and Anti-goals (outcomes that would spoil it even if the code worked) sections. Compare viable approaches and give concrete gameplay examples of success and failure. Distinguish user decisions, proposed tuning, choices left to the builder, automated acceptance and in-game checks. Choose the other sections to answer real questions about the feature. The [player settings spec](docs/superpowers/specs/2026-11-16-player-settings-design.md) separates design decisions from choices left to the builder. The [road placement spec](docs/superpowers/specs/2026-11-16-cop-spots-by-road-design.md) explains what the current code does. The [Pigeon helicopter spec](docs/superpowers/specs/2026-11-17-pigeon-helicopter-design.md) records what was proven in game. Identify engine assumptions that still need a check. Hand over the reviewed written spec before drafting the plan unless the user asks for a combined handoff.
- Write plans so another agent can execute each task from its files, input fixtures, expected observations and verification commands. Break up steps that combine several decisions or checks. The [player settings plan](docs/superpowers/plans/2026-11-16-player-settings.md) shows the expected level of detail.
- Give each feature or fix batch its own branch and worktree. For longer jobs, keep a progress checklist visible to the user. The coordinator tracks the plan and dispatches a fresh implementer for each task. Give the implementer the worktree, requirements and relevant context. The implementer tests, commits and self-reviews the change.
- Automatically dispatch a separate reviewer for each task to check both requirements and code quality. Send actionable findings back to an implementer and have the fixes independently re-reviewed. Keep moving through approved work. Before merge, have a fresh reviewer examine the full branch diff, including interactions between tasks.
- Whenever the main implementer or reviewer is working, check main's Issues for a parallel fix batch. If none is running, assign another agent clear, independently testable issues outside the files being changed. Track them on their own fixes branch and worktree. Review each batch and keep it shippable as a separate patch. Surface issues needing a user decision or an in-game check.

Add source comments or emojis only when the user requests them.

## Verification and release

- If known inputs determine the expected result, verify it with an automated test. Use recorded round data for leaderboard ranking and assist thresholds, and sampled positions and speeds for catch timing. Add a missing regression test when needed. A passing test closes that part of the check.
- Ask for a player playtest only when an open question depends on what BeamNG or BeamMP actually does, or what the player sees, hears or feels. Use an engine probe or logs first when they can answer the question. For a trailer restore, tests can verify the requested hitch nodes. The player check is whether the trailer follows when the tow car pulls away.
- For each manual check, give the shortest setup and action, the observable pass condition, and the uncertainty it resolves. Request a second player only when observing a second client is essential, such as comparing the same lightning strike across clients. Apply this rule to each check within a mixed batch.
- Keep game-side Lua compatible with BeamNG's LuaJIT. Check each changed game-side Lua file with `luajit -bl path/to/file.lua >/dev/null`. Run `make test` for Lua changes and `make vuecheck` for UI changes. When verifying a release, run `make package` to build the client ZIP and server payload. Use `docs/DEPENDENCIES.md` to locate upstream APIs and compatibility checks.
- Stage reviewed gameplay and UI changes on the local test server. Extract `git archive <reviewed-sha>` into a disposable directory and work from that snapshot. Set `test_server` to the absolute path of the main checkout's `.testserver`. If it has an installed config, first run `cp "$test_server/Resources/Server/CopsAndRobbers/config.json" server/CopsAndRobbers/config.json` in the snapshot to preserve the local settings. Then run `make install-local TESTSERVER="$test_server"`, restart the local BeamMP server from `.testserver`, and report the SHA and what to test. The user handles game or launcher restarts.
- For changes that require in-game verification, wait for the user's local playtest result or explicit deferral before merging or deploying. Record deferred tests under **In-game checks** in main's `TODO.md` with the steps and expected result.
- For engine-dependent questions, use a temporary GE extension in `~/.local/share/BeamNG/BeamNG.drive/current/lua/ge/extensions/` and read its tagged output in `~/.local/share/BeamNG/BeamNG.drive/current/beamng.log`. Give the user one comment-free GE console line with statements separated by `;`. Use freeroam for console experiments and request screenshots for placement or visual tuning. Ask before deleting a probe from the user's game folder.
- To release, run `make version V=x.y.z`. It builds the version commit on top of `origin/main`, pushes `release/x.y.z` and opens the release PR; merging that PR publishes the release. Keep version numbers out of feature plans and branches. Tests use `CNR_VERSION`. Run the relevant checks on merged main before clearing its ledger entry.
- Deploy live with `make deploy` only when the user requests deployment. Verify that the server logs show the expected version loaded and check for Lua errors. A previous release's approval applies to that release alone.
